WHY NATE EXISTS

Make everyday programs easier to understand.

Installation

Nate’s interpreter builds on macOS and Linux without LLVM. The release candidate reports nate 1.0.0-rc.1.

On macOS, install Xcode command-line tools with xcode-select --install. On Debian/Ubuntu, install build-essential, git, and libsqlite3-dev:

sudo apt-get update
sudo apt-get install build-essential git libsqlite3-dev
git clone https://github.com/mind-code-ai/nate-lang.git
cd nate-lang
make -C src
./src/nate --version
./src/nate run examples/hello.nate

Source builds use the library in the checkout. Release archives contain bin/nate and share/nate/stdlib; preserve that layout and add the archive’s bin directory to PATH. The binary resolves its own location, so programs can run from another directory. NATE_STDLIB can point to an explicit library directory, including for C embedding. Project-local libraries and modules take precedence.

To verify a source checkout:

python3 scripts/release_audit.py
python3 scripts/conformance.py
python3 scripts/http_contract.py
python3 scripts/install_contract.py

LLVM AOT and the bytecode VM are optional preview backends. Their availability does not imply compatibility with every frozen interpreter feature.

Hello world

Save this as hello.nate:

func main() {
    print("Hello, Nate!")
}

Run nate run hello.nate, or nate hello.nate. Both print just Hello, Nate! and a newline. --ast and --verbose opt into compiler diagnostics.

A file may instead contain top-level statements. If it declares main, ordinary top-level initialization runs first, followed by a zero-argument main call. Functions return nil unless they use return. Main’s returned number does not set the process exit code.

greeting = "Hello"
func main() { print(greeting + ", Nate!") }

Run nate for the REPL, or continue with variables.

REPL

Run nate or nate repl. Enter an expression to see its result. Definitions and captured values survive later input. :help, :quit, and :clear are available, with the aliases :h, :q, and :c.

Braces, parentheses, and array brackets support multiline input. Delimiters inside strings and comments do not affect continuation. Close string literals on the entered line. A line is limited to 4095 bytes and a buffered input unit to 32767 bytes; longer input is rejected rather than executed in fragments. The source-file limit is specified separately for nate run.

Use files and nate test for repeatable programs. REPL state is local to that process; there is no automatic history persistence or package installation.

Variables and constants

Assignment creates a binding or updates an existing binding in the scope chain. Values are dynamically typed. A const blocks ordinary rebinding, but does not make referenced containers immutable.

const LIMIT = 3
values = [1, 2]
alias = values
alias[0] = 9
print(values[0], LIMIT)

Integers are signed 64-bit values on the release platforms. Overflow is a recoverable error. Strings are immutable byte sequences; lengths and indexes count bytes. Array and string negative indexes are errors. Nil, false, and integer zero are falsey; empty strings and containers are truthy. The fallback operator has its own rules and preserves integer zero.

See types and values.

Functions

Functions require exactly the declared number of arguments and evaluate them left to right. Return explicitly; an ordinary last statement is not a return.

func add(a, b) { return a + b }
func no_value() { x = 1 }
print(add(20, 22))
assert_eq(no_value(), nil)

Functions use their defining file/module scope. Function values can be passed, returned, stored in arrays, and called. User callables shadow builtins with the same name. Default and variadic parameter declarations are outside the frozen API.

See closures and the function contract.

Control flow

If selects a branch. For loops support condition-only, three-clause, and array iteration forms. Break exits a loop and continue moves to its next iteration.

total = 0
for value in [1, 2, 3] { total = total + value }
if total == 6 { print("six") } else { print("unexpected") }
for i = 0; i < 2; i = i + 1 { print(i) }
switch total {
    case 6 { print("matched") }
    default { print("other") }
}

Switch does not fall through. Match supports patterns and bindings:

value = [1, 2, 3]
match value {
    case [first, ...rest] { print(first, len(rest)) }
    case _ { print("empty") }
}

A match without a successful arm returns an error. See statements and patterns.

Arrays, maps, and sets

Arrays are mutable and zero-indexed. Maps use string keys. Missing map keys return nil; comma-ok lookup distinguishes a missing key from a stored nil.

values = [1, 2]
push(values, 3)
print(values[0], pop(values))
record = map_create()
record["answer"] = 42
answer, ok = record["answer"]
assert(ok)
print(answer, map_size(record))
tags = set_create()
set_add(tags, "release")
assert(set_has(tags, "release"))

Use len for arrays and strings, map_size for maps, and set_size for sets. Indexing outside an array/string or using a negative index is an error. Assignment aliases containers. Direct container equality is unsupported; compare scalar elements or use a suitable representation for the task.

The collections module provides transformations and callbacks. Queue and stack native handles remain preview.

Structs and methods

Struct fields are untyped names. Omitted fields are nil; unknown fields are an error. Methods dispatch on a value’s runtime struct type.

struct Point { x, y }
func (p Point) sum() { return p.x + p.y }
point = Point{x: 20, y: 22}
print(point.x, point.sum())

There is no frozen field-assignment syntax. Construct a replacement instance to change scalar fields. Arrays and maps stored in fields remain mutable. Generic struct declarations are preview.

See the struct contract.

Errors and recovery

Use or for a fallback. Nil, false, runtime errors, Option.None, and Result.Err select the fallback; zero and empty strings do not. Some/Ok unwrap their payload.

func divide(a, b) {
    if b == 0 { return nil }
    return a / b
}
print(divide(10, 0) or -1)

A guard stops at the first runtime error, panic, or Result.Err statement and runs its handler. Nil and false do not fail a guard.

guard {
    value = [1][9]
} on error message {
    print(message)
}
print("continued")

Functions can return [value, error_message] and callers can unpack it with value, err = function(). A nonempty error-message string is truthy in if err; nil is falsey. A top-level on-panic handler runs once and ends the program, without resuming at the panic site. There is no try/catch or throw syntax.

See the error contract.

Closures

Closures capture their current environment by reference. Captured mutation remains visible after the defining function returns.

func counter() {
    value = 40
    return func() {
        value = value + 1
        return value
    }
}
next = counter()
print(next(), next())

The collector retains reachable environments and reclaims unreachable closure cycles. Container arguments still alias their containers; capture is not an isolation boundary. See functions and memory management.

Interfaces

An interface specifies method names and explicit argument counts. A struct satisfies it when those methods are available. Implements takes the interface name as a string.

interface Reader { read() }
struct Text { content }
func (t Text) read() { return t.content }
text = Text{content: "hello"}
assert(implements(text, "Reader"))
value, ok = text.(Reader)
assert(ok)
print(value.read())

A direct assertion, such as text.(Reader), returns the original value or an error. Comma-ok assertions return nil/false on mismatch. Assertions do not convert numbers or wrap a value in an interface object. Interfaces and methods can be exported by modules. See the contract.

Modules

Import a module using a string path. Capitalized declarations are exported into the importing scope without a module qualifier.

import "math"
print(PI, Max(20, 42))

Use import "./helpers" for a file beside the importer. The .nate extension is added during resolution. Private lowercase helpers stay in their defining scope. Functions keep that scope when called by another module. Existing files are canonicalized and cached; duplicate imports reuse exports and cycles are errors.

Project stdlib directories take precedence, then files beside the importer, then NATE_STDLIB and the library bundled with the executable. Relative paths bypass library lookup. Import collisions replace earlier bindings; choose modules deliberately when they export the same names. Qualified math.PI is unsupported.

Package manager commands and remote package caches are preview. See the module contract.

Structured concurrency

Use a concurrent block to give related tasks a shared lifetime. Each spawn starts a function call. The block waits for every task it started before the next statement runs.

Wait for related tasks

Save this as tasks.nate and run nate run tasks.nate:

func prepare(name) {
    sleep(10)
    print(name, "ready")
}

concurrent {
    spawn prepare("Report")
    spawn prepare("Summary")
}

print("Both tasks finished")

One possible output:

Report ready
Summary ready
Both tasks finished

The first two lines can appear in either order. Both tasks finished always prints last because execution leaves the block only after both tasks finish. Only spawn statements belong inside concurrent; put setup and follow-up work before or after it.

Outside a concurrent block, spawn starts a task and waits for it immediately. Use the block when you want several tasks to make progress together.

Collect results with channels

Channels let tasks return values to the code coordinating them. Each worker enqueues its result. After both workers finish, the caller receives the values and adds them together:

channel results
func square(n) { send(results, n * n) }

concurrent {
    spawn square(3)
    spawn square(4)
}

total = receive(results) + receive(results)
assert_eq(total, 25)
print("Both tasks finished:", total)
close_channel(results)

This prints Both tasks finished: 25. The sum is the same regardless of which worker sends first. Use channels to exchange values rather than depending on task scheduling order or mutating a shared result variable.

send enqueues and returns; it does not wait for a receiver. receive waits until a value is available or the channel is closed and drained. Queued values remain available after closure. value, ok = receive(results) distinguishes a queued nil from the end of a closed channel. Channels have no fixed capacity.

Recover after the tasks finish

A task failure is returned after every started task has been joined. Place a guard around the block to handle that failure:

channel completed
func failed_job() { panic "Job failed" }
func completed_job() { send(completed, "Other task finished") }

guard {
    concurrent {
        spawn failed_job()
        spawn completed_job()
    }
} on error message {
    print("Handled task failure")
}

print(receive(completed))
close_channel(completed)

This prints Handled task failure followed by Other task finished. A failed task does not automatically cancel a sibling. The handler runs after joining; a sibling blocked on a channel must still be given a way to finish.

Execution boundaries

The interpreter serializes Nate evaluation with one lock. Blocking receive, sleep, await, and task joins yield that lock so other tasks can make progress. Structured concurrency does not promise parallel CPU execution.

Captured state is shared, not copied. Static analysis catches some visible shared writes but is not complete race detection. Use channels and avoid depending on scheduling order. Task groups have no automatic timeout or cancellation; programs must arrange channel closure or other progress.

Async/await, supervision, links, monitors, and shared wrappers remain preview. See the concurrency contract for the full interpreter semantics.

Design by Contract

Preview: these APIs are outside the 1.0 compatibility contract.

Nate supports Design by Contract with expects and ensures clauses.

Overview

Design by Contract (DbC) lets you specify:

  • Preconditions (expects) — What must be true when calling a function
  • Postconditions (ensures) — What will be true after the function returns

Expects (Preconditions)

Use expects to validate inputs:

func divide(a, b) {
    expects b != 0, "divisor cannot be zero"
    return a / b
}

divide(10, 2)  # OK - returns 5
divide(10, 0)  # Error: divisor cannot be zero

Multiple Preconditions

func create_user(name, age) {
    expects name != "", "name is required"
    expects age >= 0, "age cannot be negative"
    expects age < 150, "age seems unrealistic"

    return User{name: name, age: age}
}

Ensures (Postconditions)

Use ensures to validate outputs:

func absolute(x) {
    ensures result >= 0, "result must be non-negative"

    if x < 0 {
        return -x
    }
    return x
}

The special variable result refers to the return value.

Multiple Postconditions

func clamp(value, min, max) {
    ensures result >= min, "result below minimum"
    ensures result <= max, "result above maximum"

    if value < min {
        return min
    }
    if value > max {
        return max
    }
    return value
}

Combined Example

func square_root(x) {
    expects x >= 0, "cannot compute square root of negative"
    ensures result * result == x, "result must be valid"

    return sqrt(x)
}

Benefits

1. Self-Documenting Code

Contracts make function requirements explicit:

func process_order(order) {
    expects order != nil, "order is required"
    expects order.items != [], "order must have items"
    expects order.customer != nil, "customer is required"

    # The contracts tell you exactly what's needed
}

2. Early Error Detection

Contracts fail fast with clear messages:

Error: [line 5, col 4] contract violation: divisor cannot be zero

3. Debugging Aid

When something goes wrong, contracts help pinpoint the cause.

When to Use Contracts

Good Use Cases

  • API boundaries — Validate inputs from external callers
  • Critical functions — Ensure correctness in important code
  • Complex invariants — Document non-obvious requirements

Avoid Overuse

# Too much - makes code noisy
func add(a, b) {
    expects type(a) == "int"
    expects type(b) == "int"
    ensures type(result) == "int"
    return a + b
}

# Better - simple functions don't need contracts
func add(a, b) {
    return a + b
}

Practical Example

struct BankAccount {
    owner, balance
}

func (a BankAccount) withdraw(amount) {
    expects amount > 0, "withdrawal amount must be positive"
    expects amount <= a.balance, "insufficient funds"
    ensures a.balance >= 0, "balance cannot go negative"

    a.balance = a.balance - amount
    return a
}

func (a BankAccount) deposit(amount) {
    expects amount > 0, "deposit amount must be positive"
    ensures a.balance > 0, "balance must increase"

    a.balance = a.balance + amount
    return a
}

func transfer(from, to, amount) {
    expects amount > 0, "transfer amount must be positive"
    expects from.balance >= amount, "insufficient funds"

    from = from.withdraw(amount)
    to = to.deposit(amount)

    return [from, to]
}

Best Practices

  1. Clear messages — Tell what went wrong
  2. Check inputs — Validate what you receive
  3. Document invariants — Express business rules
  4. Don’t duplicate — If the language already checks, skip the contract

Capabilities, taint, and scoped execution

Status: frozen for the tree-walking interpreter. VM and AOT are preview.

Capabilities

Capability names are file_read, file_write, network, env, exec, and unsafe. Unknown names and non-string arguments return errors. The ordinary CLI enables file reads, file writes, networking, and environment access. Programs are trusted scripts with the operating system permissions of the process that runs Nate.

OperationResult
grant_capability(name)Enables the named flag and returns true; denied inside sandbox.
has_capability(name)Returns whether the named operation is allowed in the current scope.
require_capability(name)Returns true when allowed, otherwise an error recoverable with or or guard.

Every operation takes exactly one argument. File reads, imports, and existence checks require file_read. Writes and appends require file_write. TCP and HTTP client operations require network. Preview SQLite operations require both file capabilities. A combined host capability check succeeds only when every requested flag is enabled; CAP_NONE always succeeds.

env, exec, and unsafe are reserved capability flags. Granting one does not create a new environment, subprocess, or unsafe-memory language API. Grants in ordinary trusted code can expand permissions: these functions do not establish an embedding boundary for arbitrary hostile scripts.

Scoped execution

sandbox(fn) calls a synchronous, zero-argument function or closure and returns its result. is_sandboxed() takes no arguments and reports whether execution is currently inside such a callback. Nested calls remain restricted.

Inside the callback:

  • File operations and imports return security errors.
  • Capability grants return security errors and leave permissions unchanged.
  • TCP, HTTP, WebSocket, SQLite, MCP, agent, and AI integrations are denied.
  • spawn, concurrent, supervise, and async calls are denied, preventing callbacks from queuing work that runs after the restriction ends.

The restriction ends on success, error, or panic. or and guard recover as usual. A callback that needs arguments or is not callable returns an error. Callbacks can access their captured values and change application state. This is an interpreter capability scope, not operating system isolation, memory isolation, or an execution-time/memory quota.

Taint

taint(value) returns a copy of the value tagged user. is_tainted(value) reports whether a tag is present. get_taint(value) returns none, user, file, network, or env. Each takes exactly one argument and propagates argument evaluation errors.

File text is tagged file; TCP receive results and HTTP response maps are tagged network. Values obtained by indexing a tagged container inherit its tag. JSON decoding carries source taint into parsed values; encoding also collects taint from nested values.

Arithmetic, concatenation, slicing, case conversion, trimming, splitting, formatting, copying, and builtin transformations preserve explicit input taint. When several origins contribute, one origin is retained; tags are not a set of all sources. Control flow is not tracked as information flow.

File paths passed to read_file, write_file, append_file, and file_exists must be untainted. File content may be tainted: writing data does not interpret that data as a path or command.

untaint(value) explicitly removes the tag on the returned value. sanitize(value) is a compatibility alias. Neither validates input, escapes content, nor changes the original variable. Validate the path for the intended operation before clearing its tag. Removing a container tag does not remove tags already stored on individual elements.

Nate 1.0 Specifications

This directory is the source of truth for Nate 1.0.

User docs in docs-site/ teach the language. Specs here define it. If docs and specs disagree, the spec wins and the docs must change. If code and a frozen spec disagree, the code is a bug.

How a feature becomes 1.0

  1. Write a normative spec with examples and illegal programs.
  2. Add conformance tests that quote the spec section.
  3. Make the tree-walking interpreter pass those tests.
  4. Make the VM match, or mark the feature interpreter-only.
  5. Update user docs from the spec.
  6. Mark the section frozen in 1.0-scope.md.

A feature with code but no spec is not 1.0. A spec with no conformance test is not frozen.

Status labels

  • Frozen: syntax and semantics will not change in a breaking way after 1.0.
  • Draft: spec is being written from the current implementation.
  • Preview: implemented, documented as unstable, may change after 1.0.
  • Out: not part of 1.0. Keep it off the getting-started path.

Parity definition

Two runs match when:

  • Exit codes are equal.
  • Program stdout is equal after stripping interpreter/VM banners.
  • Both succeed, or both fail with the same class of error: parse, analysis, or runtime.

Timing, thread interleaving, and map iteration order are not required to match unless a test pins them.

Analysis vs execution

Static analysis in src/analyzer*.c runs before the interpreter. Data-race errors and ownership errors that reject a program are part of the language if they are frozen.

The VM path currently skips some of that pipeline. Until it does not, those programs are interpreter-only.

Promotion path

A preview runtime becomes frozen only when:

  1. It has a spec section in this file.
  2. The frozen conformance set is green on that runtime in CI.
  3. Missing features are empty, or listed as interpreter-only in the language spec, not discovered by users.

Do not promote the VM or LLVM as part of tagging v1.0.0.

Known preview limitations

The VM skips interpreter analysis, executes spawn/concurrent synchronously, and does not implement guard or scoped capability callbacks. Direct interface assertions, module export isolation, and interpreter memory ownership are not VM compatibility promises. Its parity audit is informational and may fail. LLVM AOT requires an LLVM-enabled build and has incomplete builtin coverage. Neither backend is promoted by a candidate or stable interpreter tag.

Lexical structure

Status: frozen for the 1.0 interpreter.

Source is NUL-free text. UTF-8 text is preserved in strings; identifiers use ASCII letters, digits, and underscore, beginning with a letter or underscore. Identifiers are case-sensitive and limited to 127 bytes. _ alone is a pattern wildcard. Keywords, including preview keywords, cannot be identifiers. in is an ordinary identifier recognized contextually by a for-in loop. The reserved error token introduces a guard handler. See 00-overview.md for keywords.

# begins a comment through the end of a line. Spaces, tabs, and carriage returns are skipped; newline tokens separate statements. Blocks accept newline separators. Array elements and call arguments can span lines, including a newline before the closing delimiter; a trailing comma is allowed there. An operator and its following operand belong on the same expression line.

Integers are decimal, including leading zeros. A decimal point followed by a digit makes a float. Exponent notation and hexadecimal literals are not frozen. Out-of-range integers and nonfinite float literals are compile errors. Negative integers are a unary-minus form, including the minimum 64-bit value.

Strings use double quotes. The escapes are \n, \r, \t, \\, and \". For another escaped byte, the backslash is discarded: "\q" means "q". A string may contain a literal newline. An unterminated string is an error. There is no interpolation, single-quoted string, or NUL string value.

Operators: + - * / % = == != < <= > >=, and, or, not. Delimiters: ( ) { } [ ] , : ; .; ... is three dots in a rest pattern. -> and @ are reserved tokens; decorators are preview.

Types and values

Status: frozen for the 1.0 interpreter.

Frozen values are nil, bool, int, float, string, array, map, set, error, function/closure, struct, enum, and interface definitions. Variables are dynamic; type(value) reports the runtime type. An int is a signed 64-bit host long on the supported macOS/Linux targets. Float is a C double. Arithmetic on integers checks overflow. Mixed int/float arithmetic converts the integer to double; integer division truncates toward zero and remainder follows the dividend.

In conditions and not, nil, false, integer zero, and errors are falsey. All other values are truthy, including an empty string, empty containers, and floating zero. Errors normally propagate before a condition is evaluated. The or fallback test is specified separately in 10-errors-and-panics.md: it does not treat integer zero as failure.

Strings are immutable NUL-free byte sequences. Length and indexing count bytes. Arrays are mutable, ordered, zero-indexed sequences. Maps use string keys; missing keys return nil. Array/string indexes must be in range integers. Map and array index assignment replaces a value; invalid types or bounds return errors. Sets contain strings and are operated on through collection builtins. len accepts arrays and strings; use map_size or set_size for those types.

Scalar equality is defined for nil, booleans, strings, and numbers. Mixed numeric types compare numerically. Comparing anything to nil is allowed. Equality or ordering of unsupported non-scalar operands returns an error; there is no implicit structural equality for arrays, maps, structs, or enums. Numeric ordering is defined; string ordering is not frozen.

Assigning a container, struct, or closure aliases its storage. Mutations of an array or map are visible through aliases. Strings share immutable storage. Function scopes and captured environment lifetimes are described in 05-functions-and-closures.md and 13-memory-and-gc.md.

Statements

Status: frozen for the 1.0 interpreter.

Assignment uses name = expression. It updates an existing binding in the scope chain, or creates one in the current scope. const name = expression creates a binding that ordinary assignment cannot change. Redefining declarations replaces same-scope bindings, including at the REPL; a const is not deep immutability. Blocks ordinarily share their surrounding scope. Calls and match arms introduce environments. Loop variables remain in the enclosing environment.

a, b = array unpacks the first two values. Too few values is an error; extra values are ignored. Two-result map lookup, channel receive, and type assertion have dedicated comma-ok behavior: an existing nil value still has ok=true.

if condition { ... } else if condition { ... } else { ... } selects a branch. if initializer; condition { ... } evaluates its initializer before the condition. The condition uses truthiness from 02-types-and-values.md.

Loops: for condition { ... }, for init; condition; step { ... }, and for item in array { ... }. For-in accepts arrays; maps are not iterable through this form. break exits the loop and continue advances to the next iteration (including the step of a three-clause loop).

switch value { case expression { ... } default { ... } } evaluates case expressions in order and runs the first equal case, with no fallthrough. Cases compare same-type integers, floats, bools, and strings. If no case matches, default runs if present, otherwise the result is nil. Pattern matching is a separate form defined in 09-pattern-matching.md.

Imports and declarations are processed before ordinary top-level initialization. Functions, structs, interfaces, and enums are registered before constants; constants then initialize in source order. Ordinary top-level statements run in source order. If the unit declares a zero-argument main, it is called after initialization. Imported modules load declarations and constants, not arbitrary top-level statements or a module main. Returning an int from main does not set the process exit code. Entry point arity errors are runtime errors.

Functions and closures

Status: frozen for the 1.0 interpreter.

func add(a, b) { return a + b } declares a named function. func(x) { return x * 2 } is a closure expression. Parameters are untyped names; there are no frozen optional, default, or variadic parameter declarations. Arguments must match arity exactly and evaluate left to right. An argument error stops the call. Calls support more than sixteen arguments without a fixed stack buffer. Recursion is permitted up to the documented evaluation-depth limit.

return expression leaves the current function or closure. Bare return and falling off a function return nil; the last ordinary statement is not an implicit function return. Runtime errors still propagate. return cannot be used to escape an enclosing function from a called function.

Calls create an environment whose parent is the declaration’s scope. Named functions execute in their defining file/module scope, not their caller’s scope. Closures capture the current environment by reference, so later mutation remains visible. Assigning to a captured binding updates it. Arguments holding containers share those containers. Unreachable closure cycles are reclaimed by tracing.

Functions and closures are values: store, pass, return, and call them through identifiers, arrays, or other expressions. A user callable shadows a builtin with the same name. Calling an invalid value or using the wrong arity returns an error recoverable by guard/or.

Methods are specified in 06-structs-and-methods.md. Generic function parameters, expects/ensures contracts, strict ownership, and async/await remain preview.

Tests: tests/conformance/functions_test.nate, tests/conformance/arguments_test.nate, tests/conformance/expr_test.nate, and tests/conformance/runtime_memory_test.nate.

Structs and methods

Status: frozen for the 1.0 interpreter.

struct Point { x, y } declares named, untyped fields. Fields can be separated by commas or newlines. Point{x: 1, y: 2} constructs an instance. Omitted fields are nil; an unknown field name returns an error. Initializers evaluate in order. The struct type must be declared. Field access is point.x; accessing an unknown field or accessing a field of nil is an error. Names are case-sensitive.

func (p Point) sum() { return p.x + p.y } declares a method. The receiver is bound as the first local binding, followed by the method’s explicit parameters. point.sum() dispatches using the runtime struct type and method name. Arity must match exactly. Methods execute in their defining module scope.

Struct assignment aliases the instance. There is no frozen point.x = value assignment syntax; construct a replacement instance to change scalar fields. Arrays/maps stored in fields remain mutable through their ordinary index APIs. Rebinding the receiver variable does not replace its caller’s binding.

Generic structs may parse but remain preview. Struct equality is not structural; use fields or pattern matching to compare supported values.

Tests: tests/conformance/structs_test.nate, tests/conformance/type_contract_test.nate, and tests/conformance/arguments_test.nate.

Interfaces and type assertions

Status: frozen for the 1.0 interpreter.

interface Reader { read() } declares required method names and explicit parameter counts. implements(value, "Reader") returns whether a struct has every named method with that arity; no explicit implements declaration is needed. The second argument is a string, not an interface value. Unknown interfaces or non-struct first arguments are errors. Interfaces can be exported by modules. The runtime definition is a value used for checking, not an interface wrapper that changes method dispatch.

value.(Type) returns the original value when its runtime type matches, or a recoverable error otherwise. result, ok = value.(Type) returns original/true on success and nil/false on mismatch. It does not coerce numeric values. Supported names are int, float, bool, string, array, map, set, func, a declared struct or enum name, or an interface satisfied by a struct. Interface satisfaction uses method names and arities in the current scope, including module methods. An error evaluating the original expression propagates before the type test.

Example: file, ok = candidate.(Reader). If ok is true, file.read() dispatches on the candidate’s struct type as usual.

Generic interfaces and reflection APIs beyond the documented checks remain preview.

Enums

Status: frozen for the 1.0 interpreter.

enum Color { Red, Green, Blue } declares zero-payload variants. enum Result { Ok(value), Err(message) } declares one-payload variants. Construct a zero-payload value with Color.Red, and a payload value with Result.Ok(42). Payload variants require exactly one argument; zero-payload variants cannot be called. Unknown variants and invalid arity return errors. Variants are separated by commas or newlines. Multi-payload variants are not frozen; store an array or struct in a single payload instead.

Values retain enum and variant names plus an optional payload. Inspect them with match patterns or type assertion. Direct enum equality is unsupported and returns an error; matching compares names and extracts payloads.

The enum names Option and Result have additional fallback behavior: Option.Some(x) and Result.Ok(x) unwrap through or; None and Err use its fallback. Guard treats Result.Err as a failure. User declarations with those names have the same behavior; these are name-based runtime conventions. Import the corresponding stdlib module for constructors and helper functions.

Pattern matching

Status: frozen for the 1.0 interpreter.

match expression { case pattern { body } case _ { fallback } } evaluates the subject once, then tries arms in source order. The first matching arm with a successful guard runs. If no arm matches, the result is a runtime error. An arm body produces its final statement value as a match-expression result; explicit return still exits the surrounding function. Every arm requires case.

Patterns: integer, float, string, bool, nil, wildcard _, identifier binding, array [first, second], array rest [first, ...rest], struct Point{x: 0, y}, and enum Result.Ok(value) or Color.Red. Identifiers bind rather than compare existing variables. A struct shorthand field binds that field. _ ignores a value or payload. String literals use the same escapes as ordinary expressions. Fixed array patterns require exact length; a rest pattern binds the remaining elements to an array.

Each attempted arm has a fresh child scope for bindings. Failed arms and their guards do not leak pattern bindings. case pattern if condition { ... } requires a boolean true guard to run; another value or false moves to the next arm. Guard runtime errors propagate. This guard expression differs from the guard error-handling statement. Existing outer variables may still be updated by the arm’s ordinary assignments.

There is no static exhaustiveness guarantee. Include a wildcard when appropriate. Switch remains a separate value-comparison statement.

Tests: tests/conformance/match_test.nate, tests/conformance/expr_test.nate, and tests/negative/match_no_arm.nate.

Errors and Panics

Status: frozen for the 1.0 interpreter. guard is implemented in the interpreter; the VM rejects it.

Nate has no try and no exceptions. Failures are values. Recovery stays on the page.

Failure values

These are failures for or:

  • A value of type error
  • nil
  • false
  • Result.Err(e)
  • Option.None

Result.Ok(v) and Option.Some(v) succeed. or unwraps them to v.

Strings, including empty strings, succeed for or. An error-pair string is truthy in if err; nil is falsey, so there is no err != nil requirement. A runtime error itself normally propagates before condition evaluation.

or

result = divide(a, b) or 0
config = read_file("config.json") or "{}"
value = get_from_cache() or get_from_db() or default_value

Evaluate the left expression.

  • If it is Result.Ok(v) or Option.Some(v), the result is v.
  • If it is a failure value, evaluate the right expression and return that.
  • Otherwise return the left value.

or groups left to right and may be chained. Each stage only runs if the previous stage failed.

If the left side panics, or clears panic mode and uses the fallback. That is how simple recovery works.

Explicit error pairs

Functions may return a two-element array [value, err]. Multi-assign unpacks it:

func parse_int(s) {
    if s == "42" {
        return [42, nil]
    }
    return [nil, "invalid number"]
}

value, err = parse_int("abc")
if err {
    print("Error:", err)
}

nil on the error side means success. A string or error value means failure. Do not invent a separate error type for 1.0 user code.

Returning nil alone also works with or:

func safe_divide(a, b) {
    if b == 0 {
        return nil
    }
    return a / b
}

result = safe_divide(10, 0) or -1

guard

guard {
    process_data()
    save_file()
} on error err {
    print("Operation failed:", err)
}

The name after on error is optional: } on error { ... }.

Statements in the guard body run in order. A statement fails when:

  • it produces a runtime error (bad index, undefined function, …)
  • it panics, directly or in a called function
  • it evaluates to Result.Err(e), including x = f() where f returns Result.Err(e)

On the first failure the rest of the body is skipped and the on error block runs. err is bound to:

  • e for Result.Err(e)
  • the error or panic message as a string otherwise, without the [line N, col M] prefix

A panic caught by guard clears panic mode, the same as or. Execution continues after the guard.

These are not failures inside guard: nil, false, Option.None. Functions that return nothing return nil, and that must not trip a guard.

return, break, and continue inside the body leave the guard normally. The handler does not run.

Variables assigned in the body or handler stay visible after the guard. No stack unwinding past the guard.

panic

panic "Out of memory"
panic expr

panic evaluates expr, sets panic mode, and yields an error value. If expr is not a string, the message is "panic".

Panic is for broken invariants, not for missing files.

One top-level on panic { ... } handler may be declared. An uncaught panic stops ordinary program execution, clears panic state, and runs that handler once. A successful handler ends the program successfully; execution does not resume at the panic site. A failing handler propagates its error and is not retried. Duplicate handlers are compile errors. Imported modules do not install a handler for the importing program.

Prefer or or guard when execution should continue after a failure.

Illegal programs

  • Using exceptions or throw. Nate has neither.
  • guard { ... } without on error. Parse error, exit code 2.

Concurrency

Status: frozen for the 1.0 interpreter.

spawn worker(args) starts a task. Its operand must be a call. Outside a concurrent block, spawn waits for completion before the next statement and returns the task’s integer ID. A failed task returns its error to the spawning statement, where guard/or can recover.

concurrent { spawn first() spawn second() } queues its spawn statements, starts their threads, and joins every started thread before returning. Only spawn statements are allowed in this block. All tasks finish even if another task fails; the first failure in spawn order is returned after joining. There is no automatic cancellation or timeout of a blocked sibling. Programs must arrange channel closure or other progress themselves.

Each task evaluates its call in the spawner’s captured scope. Calls then create their own function-local scopes. The captured environment is shared, not copied. One interpreter lock serializes Nate evaluation. Blocking receive, native sleep, await, and task joins yield that lock. This is concurrency, not a promise of parallel CPU execution. Native external integrations may serialize execution.

Channels

channel messages declares a named, thread-safe FIFO queue and binds the string "messages" as the channel variable. Channel operations accept that string.

CallBehavior
send(messages, value)Enqueue a value and return nil; it does not wait for a receiver.
receive(messages)Wait for a value, or return nil when closed and drained.
value, ok = receive(messages)True for a queued value, including nil; nil/false when closed and drained.
close_channel(messages)Close and wake receivers; repeated close succeeds.

Queued values drain after close. Sending after close or operating on an unknown name returns an error. Queues have no fixed capacity or memory quota; they are not Go-style unbuffered rendezvous channels. Queued containers and closures stay reachable until received or interpreter teardown. Repeating a channel declaration with the same name makes the newest queue the lookup target; use distinct names for independent streams.

The analyzer rejects some visible shared writes across spawned tasks. It is a conservative check, not complete race detection. Captured mutable state is not automatically copied or isolated. Prefer channels; do not depend on task interleaving or treat the interpreter as an operating-system sandbox.

Async/await, supervise, link/monitor, shared-memory wrappers, retry, and circuit breakers remain preview. An interpreter waits for outstanding async work during teardown, but that is not a frozen task API.

Rules (tested)

  • Exported names start with an uppercase letter: functions, structs, enums, constants, and methods of exported types. Lowercase names are private to the module.
  • Exported names are added to the importer’s scope unqualified. math.PI-style qualified access is not supported.
  • A module’s functions run in the module’s own scope, so exported functions may call the module’s private helpers.
  • Search order for import "name": stdlib/name.nate under the project root, then name.nate next to the importing file, then the explicit NATE_STDLIB directory and the library bundled with the executable. The project root is the nearest ancestor directory of the importing file that contains stdlib/.
  • import "./x" and import "../x" are relative to the importing file.
  • A missing module is a runtime error: Cannot open module: <path>.
  • Existing paths are canonicalized before caching. A module is initialized once; later importers receive its cached exports in their own scopes.
  • Imports are top-level declarations. Cyclic imports are runtime errors, including cycles spelled with different relative paths. Import nesting is limited to 128 modules.
  • Constants initialize in their module’s private scope after functions are registered, so private helpers can be used in constant initializers.
  • Importing a module does not re-export that module’s own imports.

Names imported later replace earlier non-constant bindings of the same name. Exports are unqualified: users must choose imports deliberately when names collide. Module initialization registers declarations and evaluates constants; arbitrary top-level assignments and module entry points do not run during import. Interfaces are exported by the same capitalized-name rule.

NATE_STDLIB is a host-supplied directory override tested by scripts/install_contract.py. The executable searches ../share/nate/stdlib (relative to its bin directory), then ../stdlib for source builds. NATE_PATH is not implemented or frozen. See cli.md.

Memory and GC

Status: frozen for the 1.0 interpreter. Implementation in src/interp_gc.c and runtime/safety.md.

Frozen 1.0 memory is the interpreter GC. LLVM AOT and the bytecode VM are preview. Their allocators are not a 1.0 promise.

Guarantees

  • Strings, errors, arrays, maps, sets, structs and enums are traced by the interpreter GC. Users do not explicitly free values.
  • nil is a value. It is not a C null pointer in user code.
  • Array and string indexes are bounds-checked.
  • Closures retain captured environments and their values. Unreachable cycles between closures and environments are collected.

Tracing uses a work queue, so deeply nested container graphs do not consume the native call stack. Collection occurs at outer statement boundaries; nested evaluation and programs with suspended tasks defer collection because their C stack temporaries are not yet explicit roots. Module environments remain roots for the lifetime of the interpreter. The last statement’s result is a temporary root across its collection point, including when a block returns an otherwise unbound string.

Parsed units own their source, nodes, names, and temporary parser allocations. Releasing a unit frees its storage iteratively, including on syntax errors. Runtime declarations retain their units, so saved REPL functions and closures do not borrow the mutable command buffer. Queued channel messages are roots for both collections and the source of any contained functions. Between REPL commands, units no longer referenced by reachable runtime values are released. Redefinitions replace the current scope’s binding rather than retaining hidden versions of old definitions. Collection is deferred while tasks or incompletely traced preview handles may hold native references. Unit references are also released at interpreter teardown.

Parser allocation cleanup, repeated runtime string/error and closure allocation, and the conformance test command run with LeakSanitizer on Linux. Native preview handles still need a separate ownership audit; their presence can defer collection. Resource quotas and bounded memory consumption are not guarantees of the current interpreter. True allocation exhaustion may terminate the process; user-level or is not an out-of-memory isolation boundary.

C embedding ownership

Text values produced during evaluation belong to the interpreter. Aliases share the same text; embedders must not free it. A returned value is borrowed until a later collection or interpreter teardown; copy text before retaining it solely in host storage across evaluations. Host C locals are not collector roots.

Outside evaluation, make_string and make_error return caller-owned copies. make_string_owned adopts a malloc buffer during evaluation and leaves it caller-owned outside evaluation. Borrowed C text supplied to evaluation remains the caller’s responsibility. Captured variable mutation remains visible through the shared environment.

Capabilities, taint, and scoped execution

Status: frozen for the tree-walking interpreter. VM and AOT are preview.

Capabilities

Capability names are file_read, file_write, network, env, exec, and unsafe. Unknown names and non-string arguments return errors. The ordinary CLI enables file reads, file writes, networking, and environment access. Programs are trusted scripts with the operating system permissions of the process that runs Nate.

OperationResult
grant_capability(name)Enables the named flag and returns true; denied inside sandbox.
has_capability(name)Returns whether the named operation is allowed in the current scope.
require_capability(name)Returns true when allowed, otherwise an error recoverable with or or guard.

Every operation takes exactly one argument. File reads, imports, and existence checks require file_read. Writes and appends require file_write. TCP and HTTP client operations require network. Preview SQLite operations require both file capabilities. A combined host capability check succeeds only when every requested flag is enabled; CAP_NONE always succeeds.

env, exec, and unsafe are reserved capability flags. Granting one does not create a new environment, subprocess, or unsafe-memory language API. Grants in ordinary trusted code can expand permissions: these functions do not establish an embedding boundary for arbitrary hostile scripts.

Scoped execution

sandbox(fn) calls a synchronous, zero-argument function or closure and returns its result. is_sandboxed() takes no arguments and reports whether execution is currently inside such a callback. Nested calls remain restricted.

Inside the callback:

  • File operations and imports return security errors.
  • Capability grants return security errors and leave permissions unchanged.
  • TCP, HTTP, WebSocket, SQLite, MCP, agent, and AI integrations are denied.
  • spawn, concurrent, supervise, and async calls are denied, preventing callbacks from queuing work that runs after the restriction ends.

The restriction ends on success, error, or panic. or and guard recover as usual. A callback that needs arguments or is not callable returns an error. Callbacks can access their captured values and change application state. This is an interpreter capability scope, not operating system isolation, memory isolation, or an execution-time/memory quota.

Taint

taint(value) returns a copy of the value tagged user. is_tainted(value) reports whether a tag is present. get_taint(value) returns none, user, file, network, or env. Each takes exactly one argument and propagates argument evaluation errors.

File text is tagged file; TCP receive results and HTTP response maps are tagged network. Values obtained by indexing a tagged container inherit its tag. JSON decoding carries source taint into parsed values; encoding also collects taint from nested values.

Arithmetic, concatenation, slicing, case conversion, trimming, splitting, formatting, copying, and builtin transformations preserve explicit input taint. When several origins contribute, one origin is retained; tags are not a set of all sources. Control flow is not tracked as information flow.

File paths passed to read_file, write_file, append_file, and file_exists must be untainted. File content may be tainted: writing data does not interpret that data as a path or command.

untaint(value) explicitly removes the tag on the returned value. sanitize(value) is a compatibility alias. Neither validates input, escapes content, nor changes the original variable. Validate the path for the intended operation before clearing its tag. Removing a container tag does not remove tags already stored on individual elements.

Defined limits

Integer arithmetic checks signed overflow, including negation of the smallest integer and its division/remainder by -1. Errors are recoverable with or and guard. Numeric literals outside the host long/finite double ranges are compile errors; the release targets use 64-bit long.

Source files, imports and read_file accept regular text files up to 64 MiB. NUL-containing text is rejected. Short reads use the actual byte count; I/O and close failures are reported. FIFOs and devices are rejected without waiting for input. Existence checks use metadata and do not read file content.

Parser recursion is limited to 256 tracked levels, analyzer traversal to 512, and evaluation to 512. Exceeding a limit returns a diagnostic. These bounds protect native stacks; they do not limit loop iterations or total allocations. Evaluation also reserves 256 KiB of native stack headroom on the supported platforms. A small host stack or sanitizer build can reach this guard before the nominal recursion limit. It returns the same depth diagnostic. If native stack bounds cannot be inspected, evaluation uses a conservative 128-level cap.

JSON nesting is limited to 128 levels and encoded output to 64 MiB. Format width and precision are limited to 255. Larger values return errors before padding buffers or numeric conversion can overflow.

Versioning

Nate 1.0 uses a three-part version: MAJOR.MINOR.PATCH.

The first public language release is 1.0.0. The current candidate prints nate 1.0.0-rc.1. Bump NATE_VERSION in src/commands.h to 1.0.0 as part of the tag.

What 1.0.0 promises

After v1.0.0, a program that uses only frozen syntax, frozen stdlib APIs, and frozen CLI flags keeps working on later 1.x releases.

Frozen means listed as frozen in 1.0-scope.md and specified in this directory.

Compatibility classes

Language (frozen). Breaking changes require 2.0. Examples: removing or, changing spawn to require a different form, making nil truthy.

Stdlib (frozen public API). Removing or renaming a documented function requires 2.0. Adding a function is a minor release.

CLI (frozen commands). run, test, bench, doc, --version, and --help keep their meaning. New flags are minor. Removing a frozen flag is major.

Preview. VM, LLVM, LSP, packages, async, supervise, move, contracts, reflection, extra HTTP, SQLite, agents. No compatibility promise. A preview flag may disappear in 1.x.

Out of 1.0. Not shipped as product. No version promise.

What may change in 1.x without a major bump

  • Bug fixes that match the frozen spec
  • Performance
  • Better error messages
  • New stdlib functions
  • New CLI commands, clearly marked
  • Preview features, including removal
  • Implementation internals: GC details, C file layout, VM opcodes

What requires 2.0

  • Changing the meaning of frozen syntax
  • Removing a frozen builtin or stdlib function
  • Changing frozen CLI exit codes in a way that breaks scripts
  • Making a preview feature frozen without a minor release that says so

Interpreter vs other runtimes

The version number describes the language and the interpreter.

nate run --vm and nate build are preview. A VM or AOT mismatch is not a 1.0 language bug unless compatibility.md has already promoted that runtime.

Command output

nate --version

must print a single line of the form:

nate 1.0.0

Optional extra lines for build features are allowed after that line:

nate 1.0.0
interpreter: yes
vm: preview
llvm: preview

nate --help lists frozen commands first. Preview commands are grouped under a Preview heading.

Tagging

  • Git tag: v1.0.0
  • C macro: NATE_VERSION "1.0.0"
  • VS Code extension may stay 0.1.x until it talks to nate lsp
  • Docs site version matches the language version

Changelog

Every 1.x release has a changelog entry that states:

  1. What frozen behavior changed, if any. Prefer none.
  2. What was added.
  3. What preview features changed.
  4. What is still not supported.

See 1.0-scope.md for the 1.0.0 product boundary.

Release candidates

Candidate tags use vMAJOR.MINOR.PATCH-rc.N and the binary reports the same version without the v prefix. Candidates are prereleases and may change before the stable tag. Native archives retain bin/nate and share/nate/stdlib, include commit metadata, and have SHA-256 checksum sidecars. The release workflow reruns the complete CI gate before building and publishing archives. Tag and manifest versions must agree. Repository visibility is unchanged by publication.
